## Executive Abstract

Decentralized Physical Infrastructure Networks (DePIN) face a fundamental epistemological vulnerability: the conflation of cryptographic authenticity with physical truth. In contemporary networks, a cryptographic digital signature generated by a private key proves only that a particular piece of software or silicon emitted the message. It provides zero formal guarantee that the asserted physical phenomenon occurred, that the sensor transducer operated within valid physical calibration limits, or that the physical environment was not actively spoofed.

The Physical Evidence Consensus (PEC) protocol addresses this vulnerability by introducing an empirical verification layer decoupled from naive message signing. Aligning with the Remote ATtestation ProcedureS (IETF RATS, RFC 9334) architectural framework, PEC treats physical telemetry not as authoritative claims, but as raw evidence assertions that must be reconciled against deterministic physical models, causal dependency tensors, and cross-transducer invariants before reaching settlement finality.

## The 5 Foundational Primitives

PEC formalizes decentralized physical verification around five discrete architectural primitives:

1. **Physical Identity**: Grounded hardware attestation linking cryptographic key material to silicon roots of trust, physical packaging, transducer authorities, and tamper-evident characteristics.
2. **Physical Evidence**: Structured, signed empirical observations accompanied by transducer calibration vectors, sampling envelopes, environmental contexts, and noise characteristics.
3. **Physical Consistency**: Deterministic graph-based reconciliation of multi-source observation streams against thermodynamic, kinematic, and electromagnetic conservation laws.
4. **Physical Work**: Formalization of thermodynamic, energetic, or computational exertion where state transitions require irreversible entropy generation or demonstrable challenge-response actuation.
5. **Physical Settlement**: Deterministic transition of evaluated physical claims into verifiable assurance states consumed by decentralized state machines, smart contracts, or dispute arbitration layers.

## The 4D Assurance Metric

Settlement in PEC does not collapse evaluation into a naive binary status. Every evaluated claim emits a deterministic 4-tuple coordinate:

$$\text{AssuranceCoordinate} = \langle \text{DecisionState}, \text{PhysicalAssurance}, \text{Freshness}, \text{SettlementFinality} \rangle$$

### 1. DecisionState
Represents the topological resolution of the evidence graph:
* `VALID`: All required physical invariants and threshold authority checks pass with zero unresolvable contradictions.
* `INVALID`: Evidence directly violates one or more fundamental conservation laws or deterministic reference bounds.
* `UNKNOWN`: Evidence is non-contradictory but lacks the requisite independence degree ($N_{eff}$) to clear threshold verification.
* `CONTESTED`: Mutually exclusive observation sets exist within the hypergraph whose conflict metric exceeds admissible error margins.

### 2. PhysicalAssurance ($PA_0 \to PA_{10}$)
Quantifies the empirical confidence depth:
* `PA_0`: Unattested raw telemetry from unknown sources.
* `PA_1 - PA_3`: Single-device hardware root of trust with basic calibration bounds.
* `PA_4 - PA_6`: Multi-source cross-validation satisfying spatial-temporal correlation envelopes.
* `PA_7 - PA_9`: Active challenge-response verification with multi-party non-colluding witnesses.
* `PA_10`: Provable physical invariant conservation validated across independent physical modalities with tamper-proof roots of trust.

### 3. Freshness ($F_0 \to F_3$)
Defines temporal bounded validity relative to physical phenomenon relaxation times:
* `F_0`: Expired or non-deterministic temporal alignment.
* `F_1`: Coarse epoch validity (within protocol cycle bounds).
* `F_2`: Bounded dynamic synchronization with verifiable challenge-nonce decay.
* `F_3`: Hard real-time causal sequence guarantee verified via monotonic hardware clocks and forward secrecy.

### 4. SettlementFinality ($SF_0 \to SF_5$)
Tracks state machine persistence and economic irrevocability:
* `SF_0`: Ephemeral observation in relayer transit memory.
* `SF_1`: Ingested into Physical Evidence Hypergraph (PEH).
* `SF_2`: Evaluated deterministically by the PEC Virtual Machine (PEC-VM).
* `SF_3`: Soft consensus achieved across relayer verification committee.
* `SF_4`: Committed to canonical ledger settlement layer.
* `SF_5`: Irrevocable settlement after contestation window expiration.

## System Architecture

```text
+--------------------------------------------------------------------------+
|                              PHYSICAL WORLD                              |
|   Thermodynamic States | Kinematic Movement | Electromagnetic Waves      |
+--------------------------------------------------------------------------+
                                     │
                                     ▼
+--------------------------------------------------------------------------+
|                           TRANSDUCERS & SENSORS                          |
|    Photodiodes | Accelerometers | Thermistors | Flow Meters | Current    |
+--------------------------------------------------------------------------+
                                     │
                                     ▼
+--------------------------------------------------------------------------+
|                      HARDWARE ROOT OF TRUST (RoT)                        |
|   Secure Element (ATECC608 / OPTIGA) | Monotonic Counter | PUF / Ed25519  |
|   -> Produces: Signed Evidence Envelope + Transducer Calibration Vector   |
+--------------------------------------------------------------------------+
                                     │
                                     ▼ [Peer-to-Peer Relayer Transport]
+--------------------------------------------------------------------------+
|                  PHYSICAL EVIDENCE HYPERGRAPH (PEH)                      |
|   Vertices: Observations, Attestations, Models, Contexts, Invariants     |
|   Edges:    Supports, Contradicts, Conditions, Derives, Depends_On       |
+--------------------------------------------------------------------------+
                                     │
                                     ▼ [Deterministic Ingestion]
+--------------------------------------------------------------------------+
|                         PEC VIRTUAL MACHINE (PEC-VM)                     |
|   - Deterministic Math Engine (PEC-MATH-01, Q64.64 Fixed-Point)          |
|   - Dependency Matrix Solver (Tensor D, Effective Independence N_eff)    |
|   - Invariant Engine (Conservation Laws I_0 to I_6, Tolerance Epsilon_E) |
|   - Conflict Resolution Pipeline (Contradiction Set Minimization)        |
+--------------------------------------------------------------------------+
                                     │
                                     ▼
+--------------------------------------------------------------------------+
|                        DOWNSTREAM SETTLEMENT                             |
|   4D Metric Coordinate: <DecisionState, PA_x, F_y, SF_z>                 |
|   Consumers: L1/L2 Smart Contracts | Proof Verification Bridges | DA     |
+--------------------------------------------------------------------------+
```

## Monorepo Layout

The repository is organized into distinct functional workspaces:

```text
depin-mesh-protocol/
├── .github/          # CI/CD workflows, issue forms, and PR templates
├── spec/             # Formal protocol specifications (RFCs) and Protobuf definitions
│   ├── proto/        # Canonical Protocol Buffers schemas (v1)
│   └── RFC-*.md      # Protocol RFC documents
├── crates/           # Core Rust implementation crates
│   ├── pec-core      # Core types, PEH primitives, and Q64.64 deterministic math
│   └── pec-vm        # Evidence evaluation runtime and invariant execution engine
├── firmware/         # Embedded device reference firmware (ESP32-S3, Secure Elements)
├── relayer/          # P2P evidence aggregation and hypergraph synchronization daemon
└── docs/             # Protocol architecture and contribution documentation
```

## Phased Delivery Roadmap

* **Phase 0: Protocol Specification & Deterministic Math (Current)**
  * RFC-0001 publication (formal protocol specification).
  * Canonical Protobuf schemas (`depinmesh.pec.v1`).
  * PEC-MATH-01 Q64.64 fixed-point specification and validation test vectors.

* **Phase 1: Core Engine & Verification Virtual Machine (`pec-core`, `pec-vm`)**
  * In-memory Physical Evidence Hypergraph (PEH) implementation.
  * Invariant solver implementing conservation models ($I_0 - I_6$).
  * Dependency tensor computation for effective evidence degree ($N_{eff}$).

* **Phase 2: Reference Embedded Firmware**
  * Reference firmware implementation for ESP32-S3 paired with hardware secure elements.
  * Deterministic attestation generation and signed evidence framing.

* **Phase 3: Relayer Network & Hypergraph Gossip**
  * Relayer peer daemon for streaming evidence ingestion.
  * Distributed conflict detection and graph pruning mechanics.

* **Phase 4: Consensus Bridges & Production Testnet**
  * On-chain zero-knowledge and state-machine verification bridges.
  * Decentralized testnet deployment with active physical telemetry workloads.
